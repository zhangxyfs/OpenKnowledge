# wiki 分支感知设计（方案 C：主干基准 + 分支差异）

- 日期：2026-08-08
- 状态：已批准（用户选定方案 C；合并场景语义与迁移方案已逐节确认）
- 目标版本：v2.6.0

## 1. 背景与问题

知识库按项目（目录名）组织，与项目的 git 分支无关。当目标项目切换分支时，wiki 内容可能与当前代码不一致：

- **wiki 结构条目**描述的是游标时刻、游标所在分支的结构；切分支后注入给 agent 的"项目结构"可能是另一条分支的现实（误导）
- **游标语义失真**：`state/wiki.json` 只记 `{last_commit, generated_at, entry_count}`（`internal/wiki/wiki.go:18`），落后判定为 `git rev-list --count <last_commit>..HEAD`（`wiki.go:97`）——切到分叉分支时该计数只算"HEAD 有而游标没有"的提交，另一边的分叉提交完全不可见；游标 commit 被 rebase/squash 改写后 rev-list 报错 → fail-open 静默不提醒
- 知识库内容的分支敏感性分两类：**经验/pitfall/mandatory 条目大多分支无关**（坑与规约跨分支成立），真正分支敏感的是 **wiki 结构条目**与游标本身

用户的分支模型（已确认）：**短期 feature 分支与长期并行多线（如 master + 长期重构分支）兼有**。

## 2. 决策记录

| 决策点 | 结论 |
|---|---|
| 总体方案 | **C：主干基准 + 分支差异**——全量 wiki 一份（显式基准分支），分支维度只维护"差异条目"；短期分支零维护（检测+提示） |
| 合并/删除分支时的条目 | **只检测+提示，绝不自动删改**（写入收敛铁律），清理经用户确认 |
| 游标 commit 被改写 | 从"静默不提醒"改为**显式失效态** |
| 旧数据迁移 | 读取时惰性升级；旧 `last_commit` 用 `merge-base --is-ancestor` 判归属，**宁可报疑不可猜错** |
| 实施分期 | 一期：分支感知检测 + 注入提示（独立可用）；二期：分支差异条目 |

被否决方案：A（纯检测提示——长期并行线下 wiki 持续描述错误的分支）；B（条目按分支全量隔离——为 5% 的分支敏感内容付全量架构税，短期分支条目膨胀）。

## 3. 数据模型

`state/wiki.json` 从单游标扩展为：

```json
{
  "base_branch": "master",
  "cursors": {
    "master": { "last_commit": "…", "generated_at": "…", "entry_count": 15 },
    "dev":    { "last_commit": "…", "generated_at": "…", "entry_count": 3 }
  }
}
```

- `base_branch`：全量 wiki 条目的基准分支
- `cursors`：按分支各记一份游标；分支删除后残留游标惰性忽略
- **分支差异条目**（二期）：普通 reference 条目，tags 含 `wiki` + `branch:<名>`，标题带分支后缀（如"架构总览（dev 分支差异）"）；只记该分支与基准的结构差异（数百字级）
- 经验/mandatory 条目不引入分支维度（YAGNI：分支专属经验在正文写明即可）

## 4. 旧数据迁移

真正需要迁移的只有 `state/wiki.json`：

| 数据 | 迁移量 |
|---|---|
| `state/wiki.json` | 单游标 → §3 新格式 |
| wiki 条目 | **零迁移**——无分支维度的旧条目天然归属基准分支 |
| INDEX.md / kb.db 向量 | **零迁移**——派生物，随下次写入自动反映 |

**迁移方式**：`LoadCursor` 读取时惰性升级（检测旧格式 → 内存升级 → 下次写盘落新格式）；任一步失败保持旧行为，绝不弄丢 `last_commit`。

**旧 `last_commit` 归属判定**（迁移时刻用户可能正切在非生成分支上）：

- `git merge-base --is-ancestor <last_commit> HEAD` **可达** → 归入当前分支（与现状语义完全等价）
- **不可达** → 不归入任何分支，进失效态提示："wiki 游标与当前分支分叉，请在生成 wiki 的分支上跑一次 `ok wiki`"

**`base_branch` 初始值** = 迁移时刻的当前分支名；长期并行线用户经 `ok wiki base [<branch>]`（新子命令，查看/设置）显式调整。

**版本混用兼容**：旧版读新格式 → `last_commit` 缺失 → 表现为"从未生成 wiki"（不崩不报错，退化为首次体验）；旧版写回旧格式 → 新版下次读再升级，无害。两端 fail-open。

## 5. 分支状态检测（CheckStatus 扩展）

当前分支取 `git symbolic-ref --short HEAD`（detach 记 `DETACHED@<short>`；git 不可用维持 Behind=-1 语义）。状态机：

| 状态 | 判定 | 表现 |
|---|---|---|
| 无基线 | 当前分支无游标 | "本分支未生成过 wiki" |
| 落后 | 游标可达 HEAD 祖先链，`rev-list --count` 超阈值 | 现有提醒（每会话一次） |
| 分叉 | 游标 commit 存在但不可达 HEAD 祖先链 | 上下文行：基准分支、游标短哈希、merge-base |
| 失效 | 游标 commit 已不存在（rebase/squash 改写） | "游标失效（分支可能被改写），建议重新生成" |
| 已并入 | 当前为基准分支，某差异分支 tip 已是 HEAD 祖先且其差异条目存在（二期） | "dev 已并入 master，差异条目已失效，建议清理" |

git 命令全部经既有 `procx` 静默执行封装；任何 git 错误 fail-open 不提醒。

## 6. 注入行为

- 当前分支 == 基准分支且无异常：**完全现状**（零行为变化）
- 非基准分支：wiki 内容注入前附一行上下文，如
  `> wiki 基于 master@abc1234；当前分支 dev，分叉点 def5678`
  该分支有差异条目（二期）则照常参与检索，标题自带分支标注
- 失效态：只附"游标失效"提示行，内容照注（fail-open 不阻断）
- 全部提示复用现有 wikiNudge 通道（每会话最多一次、预算外放行）

## 7. 合并场景语义

1. **feature 合回主干**：零特殊处理；主干游标落后 → 现有提醒驱动重扫
2. **长期分支并入基准**（dev→master）：差异条目失效——基准分支上检测"差异分支 tip 已是 HEAD 祖先"→ 提示清理（`ok wiki` 更新时给出，**用户确认才删**，分支可能继续从 master 拉出）；主干全量条目经 behind 提醒重扫后自然包含原 dev 结构
3. **反向合并**（master 进展同步进 dev）：差异条目仍有效；dev 游标照常 behind（数字因合入主干 commit 虚高，可接受）；下次在 dev 上跑 `ok wiki` 时差异条目随增量刷新
4. **rebase/squash 致游标消失**：显式失效态（§5），不再是静默
5. **基准分支迁移**：人工操作——新基准上全量重扫 + `ok wiki base` 改基准 + 按 ② 提示清理旧差异条目

## 8. ok wiki 技能行为（二期）

- 基准分支上运行：全量/增量照旧
- 非基准分支运行：只生成/更新**本分支差异条目**（对比 merge-base 以来的结构 diff），不触碰全量条目
- 检测到 §7.2 时提示清理失效差异条目
- INDEX.md 的 Wiki 目录按分支分组（差异条目归入"分支差异"小节）

## 9. 实施分期

- **一期（本 spec 主体，独立可用）**：数据模型迁移（§3/§4）+ 三态检测（§5，除"已并入"）+ 注入上下文行（§6）+ `ok wiki base` 子命令
- **二期**：分支差异条目（生成/更新/清理提示、INDEX 分支分组、§5"已并入"检测）

## 10. 错误处理与铁律

- fail-open：git 不可用/命令失败/状态损坏 → 不提醒、不影响注入主流程
- 写入收敛：合并检测只读不写；差异条目清理必须用户确认；游标迁移失败保旧行为
- 状态文件并发：沿用现有 SaveCursor 单写者假设（prompt hook 与 sidecar 均经同一 state 目录，已有 session 级并发锁先例）

## 11. 测试策略

- wiki 包：新格式 Load/Save 回环、旧格式惰性升级（可达/不可达两分支）、base_branch 缺省与 `wiki base` 设置、三态检测（临时 git 仓库构造分叉/落后/失效场景）、git 不可用 fail-open
- hook 包：非基准分支注入附上下文行、失效态提示、每会话一次去重
- 回归：基准分支上注入与现状逐字节一致（现有测试全绿）
- 二期：差异条目检索注入、INDEX 分组、并入检测提示

## 12. 明确不做（Out of Scope）

- 经验/mandatory/enforce 条目的分支维度
- 分支差异条目的自动删除、分支删除的自动感知
- 远程跟踪分支同步状态（ahead/behind remote）
- 多 worktree 场景的并发游标写

## 13. 验收标准（一期）

1. 基准分支上：注入与提醒行为与现状完全一致
2. 切到分叉分支：注入带"wiki 基于 <base>@<short>"上下文行；`ok wiki status` 显示分叉态
3. 游标 commit 被 rebase 改写：显式失效提示而非静默
4. 旧 wiki.json 升级：可达归入当前分支；不可达报疑不归错
5. `ok wiki base dev` 后 status/注入上下文以 dev 为基准
6. 全量测试绿；版本混用（旧版读新格式）不崩
